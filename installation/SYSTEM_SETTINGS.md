## Локальные диски

Хотя Spark выполняет многие вычисления в памяти, локальные диски всё равно используются:

- для данных, которые не помещаются в RAM;
- для spill-файлов;
- для хранения промежуточных результатов между stages;
- для shuffle.

Рекомендуется иметь 4–8 дисков на каждом узле без RAID — как отдельные точки монтирования.

В Linux диски рекомендуется монтировать с опцией `noatime`, чтобы уменьшить количество ненужных операций записи.

В Spark каталоги перечисляются через запятую:

```properties
spark.local.dir /disk1/spark,/disk2/spark,/disk3/spark
```

Если на этих машинах работает HDFS, Spark может использовать те же физические диски.

## Память

Spark может эффективно работать как с 8 ГиБ, так и с сотнями гигабайт памяти на одной машине.

Рекомендуется отдавать Spark не более 75% памяти. Оставшуюся память следует оставить:

- операционной системе;
- файловому кешу;
- служебным процессам;
- вне-heap и native-памяти.

Необходимый объём зависит от приложения.

Чтобы оценить потребление памяти:

1. Загрузите часть набора данных в Spark RDD.
2. Откройте интерфейс Driver:

```text
http://<driver-node>:4040
```

3. Посмотрите вкладку `Storage`.

Потребление памяти сильно зависит от:

- storage level;
- формата сериализации;
- структуры данных;
- использования кеширования.

Следует учитывать, что JVM не всегда хорошо работает с heap более 200 ГиБ. На машинах с большим объёмом RAM лучше
запускать несколько executors.

В Spark Standalone Worker запускает несколько executors в соответствии с доступными ядрами и памятью. Каждый executor
работает в отдельной JVM.

## Сеть

Когда данные уже находятся в памяти, многие приложения Spark упираются в пропускную способность сети.

Рекомендуется использовать сеть не медленнее 10 Гбит/с. Это особенно важно для операций, активно выполняющих shuffle:

- `groupBy`;
- `reduceBy`;
- SQL joins;
- пространственные joins.

Количество данных, переданных через shuffle, можно посмотреть в Driver UI:

```text
http://<driver-node>:4040
```

## Процессорные ядра

Spark хорошо масштабируется до десятков ядер на одной машине, поскольку его потоки сравнительно мало используют общие
изменяемые данные.

Рекомендуется иметь не менее 8–16 ядер на узел. Для вычислительно тяжёлой нагрузки может потребоваться больше.

После загрузки данных в память большинство приложений ограничивается либо:

- производительностью CPU;
- пропускной способностью сети.
