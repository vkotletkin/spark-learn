## Перевод и общий смысл

Стандартные настройки Linux не всегда подходят для NiFi — приложения с большим количеством дисковых операций, файлов,
потоков и сетевых соединений. Рекомендации предлагают:

- увеличить лимит открытых файлов;
- увеличить допустимое количество процессов/потоков;
- расширить диапазон временных TCP/UDP-портов;
- уменьшить время хранения закрытых соединений;
- минимизировать использование swap;
- отключить обновление времени последнего доступа к файлам (`atime`) на дисках с репозиториями NiFi.

Это полезный ориентир, но некоторые формулировки устарели или слишком категоричны.

## 1. Максимальное количество открытых файлов

```text
* hard nofile 50000
* soft nofile 50000
```

NiFi одновременно работает с файлами FlowFile, Content и Provenance Repository, журналами, сокетами, pipes и другими
файловыми дескрипторами. При низком лимите появится ошибка:

```text
Too many open files
```

- `soft` — фактически применяемый лимит;
- `hard` — максимум, до которого процесс может увеличить `soft`;
- `*` — все пользователи.

Оценка: корректно. `50000` — разумный минимум, но не универсальное значение. Часто используют `65536` или больше после
измерений.

Важно: `/etc/security/limits.conf` действует через PAM и обычно не применяется к сервисам, запущенным через systemd. Для
NiFi лучше:

```ini
# sudo systemctl edit nifi
[Service]
LimitNOFILE=65536
```

Затем:

```bash
sudo systemctl daemon-reload
sudo systemctl restart nifi
```

Лучше ограничивать конкретного пользователя `nifi`, а не всех через `*`.

## 2. Максимальное количество процессов и потоков

```text
* hard nproc 10000
* soft nproc 10000
```

Несмотря на название раздела, речь главным образом о потоках. В Linux Java-потоки учитываются как отдельные задачи, а
NiFi может создавать много потоков для процессоров, контроллеров и внутренних служб.

Оценка: идея правильная, но 10 000 не должно заменять нормальную настройку concurrency в самом NiFi. Слишком большой
лимит также позволяет ошибочной конфигурации исчерпать память.

Для systemd предпочтительнее:

```ini
[Service]
TasksMax=10000
```

`LimitNPROC` учитывает процессы и потоки суммарно по UID, а `TasksMax` ограничивает непосредственно cgroup сервиса. Файл
`90-nproc.conf` актуален преимущественно для старых RHEL/CentOS и PAM-сессий.

## 3. Диапазон временных портов

```bash
sudo sysctl -w net.ipv4.ip_local_port_range="10000 65000"
```

При исходящем соединении ОС назначает локальный временный порт. Если NiFi очень часто открывает новые HTTP, Kafka, JDBC
или Site-to-Site соединения, стандартного диапазона может не хватить.

Оценка: корректно только при большом количестве коротких соединений. Сначала лучше:

- включить connection pooling;
- использовать HTTP keep-alive;
- не создавать JDBC-клиент на каждую операцию;
- проверить число соединений в `TIME_WAIT`.

Диапазон глобален для сетевого namespace. Порты слушающих сервисов внутри этого диапазона следует добавить в
`ip_local_reserved_ports`. Кроме того, текущая документация ядра рекомендует границы разной чётности, например:

```text
net.ipv4.ip_local_port_range = 10000 65001
```

`sysctl -w` действует только до перезагрузки. Для постоянной настройки используйте `/etc/sysctl.d/90-nifi.conf`.

## 4. Время хранения `TIME_WAIT`

```bash
sudo sysctl -w net.netfilter.nf_conntrack_tcp_timeout_time_wait="1"
```

В тексте опечатка: состояние называется `TIME_WAIT`, не `TIMED_WAIT`.

Главная проблема рекомендации: этот параметр управляет записью `TIME_WAIT` в таблице Netfilter conntrack, а не
непосредственно временем жизни TCP-сокета в ядре.

Значение `1` секунда очень агрессивно. Оно может привести к проблемам с NAT/stateful firewall и запоздавшими
TCP-пакетами. Также параметр может отсутствовать, если conntrack не загружен.

Мой совет: не применять `1` автоматически. Сначала проверить:

```bash
ss -s
conntrack -S
sysctl net.netfilter.nf_conntrack_count
sysctl net.netfilter.nf_conntrack_max
```

Если действительно исчерпывается conntrack, безопаснее начать с умеренного значения, например 30 секунд, протестировать
нагрузку и наблюдать ошибки. Основное лечение — повторное использование соединений, а не радикальное сокращение timeout.

## 5. Swap и `vm.swappiness`

```text
vm.swappiness = 0
```

Swap особенно неприятен для JVM: паузы GC и обработка данных могут внезапно замедлиться на секунды или минуты.

Но формулировка «никогда не использовать swap» неверна. `swappiness=0` не отключает swap — ядро лишь старается не
использовать его до серьёзного дефицита памяти.

Оценка: `0` или `1` разумны для выделенного NiFi-сервера, но необходимо:

- правильно настроить JVM heap;
- оставить память для direct buffers, потоков и native memory;
- оставить значительный объём RAM под файловый cache;
- контролировать OOM.

Полное отключение swap (`swapoff`) повышает предсказуемость задержек, но при нехватке RAM процесс может быть убит OOM
Killer. Под cgroup v2 можно точечно запретить swap сервису через `MemorySwapMax=0`.

## 6. `noatime` для репозиториев

Пример `/etc/fstab`:

```text
UUID=... /data/nifi ext4 defaults,noatime 0 2
```

Обычно при чтении файла файловая система обновляет `atime` — время последнего доступа. Это создаёт дополнительную запись
даже при чтении. `noatime` её отключает.

Оценка: корректно и обычно безопасно для выделенных разделов NiFi. Но современные Linux по умолчанию часто используют
`relatime`, который уже значительно сокращает такие записи, поэтому прирост может быть меньше, чем утверждает
документация.

Более важные меры:

- разнести Content, FlowFile и Provenance Repository по подходящим дискам;
- обеспечить достаточный IOPS и latency;
- следить за заполнением дисков;
- не применять `noatime` ко всей системе без необходимости.

## Итоговая рекомендация

Применять сразу:

- `LimitNOFILE=65536`;
- `TasksMax=10000` либо значение на основе реальной нагрузки;
- `noatime` на выделенных репозиториях;
- `vm.swappiness=0` или `1` при корректном размере памяти.

Применять только после измерений:

- расширение `ip_local_port_range`;
- любые изменения conntrack;
- особенно `nf_conntrack_tcp_timeout_time_wait=1`.

Таким образом, документ Apache NiFi в целом задаёт правильное направление, но раздел про systemd не учитывает
современный способ запуска сервисов, а рекомендация `TIME_WAIT=1` слишком рискованна для безусловного применения.
